# 基于Snowluma的QQ自动回复—— 三端口数字跟发与「扣数字」回复工具

> 代码由 codex-GPT-6 luna 生成。
> 语言：C（MinGW-w64 GCC）　平台：Windows　协议：OneBot v11 正向 WebSocket

---

## 一、程序做什么

连接本机 Snowluma 的三个账号端口（3001/3002/3003），在指定群（1124334011）中自动完成两类回复：

1. **数字跟发**：目标 QQ（3288574505）发送图片或 @全体消息 → 开启 120 秒开关；开关期间**两个不同成员**在 30 秒内发送**相同的一位纯数字** → 3001/3002/3003 三个账号一起回复该数字，随后开关立即关闭（一张图只跟发一轮）。
2. **扣数字回复**：目标 QQ 的 @全体消息中若含「扣 + 一位数字」（如「@全体 扣3」）→ 由 3001 回复该数字；成功后关闭跟发开关并进入 60 秒冷却。

## 二、架构要点

- **检测与发送分离（三端口分工）**：
  - **3001**：唯一负责接收并判断群消息的端口（开关计时、数字配对、扣数字触发、禁言通知处理），同时也参与回复；
  - **3002 / 3003**：**不监听、不判断任何群消息**，只在"满足回复条件"（数字配对成功或扣数字触发）时，与 3001 一起各回复一条；
  - 三个账号的回复回显全部被排除，不参与任何配对或开关控制。
- **单一全局开关**：图片与 @全体共用同一个 120 秒开关，新的触发消息会清空配对表并重新计时。
- **防刷屏**：
  - 开关在触发瞬间关闭，同一轮不会重复发送；
  - 每轮每端口最多 1 条（3001/3002/3003 各一条）；
  - 扣数字 60 秒冷却、解禁重发最多 20 次、响应 2 秒兜底、绝不盲目补发；
  - 机器人三个账号自己的回显消息不参与配对（V5.0.1 修复）；
  - 陈旧消息（超过 5 秒）直接丢弃，防止积压补触发。
- **防卡顿**：
  - 启动即禁用控制台快速编辑模式（QuickEdit），运行中每 5 秒复查；
  - 有界异步日志队列：控制台即使被暂停，也只会阻塞日志线程，网络、计时、回复完全不受影响。
- **稳定性**：3001 启动时不在线会无限重连（主端口必须存活）；3002/3003 启动不可用则本次运行不参与；可用端口断线后每 3 秒自动重连；TCP_NODELAY + 250ms 发送超时；ping/pong 保活。

## 七、使用注意

1. 三个端口必须绑定**三个不同的 QQ 账号**（同一 QQ 绑多端口会导致同一人连发）。
2. 群消息事件需包含 `self_id` 字段（OneBot v11 标准字段），否则机器人回显排除与解禁通知匹配会失效。
3. 扣数字只认「扣 + 单个 ASCII 数字」；「扣贰」「扣可」不会触发。
4. 首次在真实群使用时，建议观察三条关键日志：首次配对成功、首次扣数字、首次禁言解禁重发。
5. **黑名单与机器人账号互不影响**：机器人账号（如 3002 的 QQ）即使恰好也在黑名单里，它的消息也会先被"机器人回显排除"拦截，**不会触发"黑名单消息关闭开关"**；黑名单的"关闸"逻辑只对真人成员生效（已专项测试验证）。
6. 三个端口都需要在 Snowluma 中分别登录且加入目标群；3002/3003 未启动不影响 3001 的监听，只是该轮少一个账号回复。

## 八、变更记录

- **V5.X.X**（当前版本）：修复机器人回显时序漏洞——原 V5.0.0 只排除 3001 自己账号的回显，3002/3003 的回复在"新图片已清表、旧回显晚到"的时序下会被 3001 当作真人数字参与配对，导致单真人+机器人回显凑成假配对、多触发一轮。修复方式：每个端口在收帧时各自记录 `self_id`，所有机器人账号的回显统一排除（`is_bot_qq`），且排除发生在黑名单判断之前。其余逻辑与 V5.0.0 完全一致。
- **V5.0.0**：在 V4（数字跟发）基础上恢复 V3 的「扣数字」逻辑（@全体触发、60 秒冷却、禁言等待与解禁重发），并新增「@全体消息」作为开关触发源、黑名单消息立即关闸。
